## 一、项目概述

### 1.1 项目背景

高校学生面临"每天吃什么"的选择困难，同时对饮食健康管理意识逐渐增强。本项目旨在打造一个面向校园食堂的 AI 辅助饮食平台，通过**转盘随机、卡片滑动**、**菜品点评排行**、**AI 营养分析**和**菜品搜索**等核心功能，提升学生就餐体验。推荐页聚合广告、待点评提醒和转盘、卡片、榜单入口，不生成个性化推荐列表。

### 1.2 目标用户

| 用户类型 | 描述       | 核心诉求             |
| ---- | -------- | ---------------- |
| C端学生 | 在校大学生    | 快速选菜、发现好菜、管理饮食健康 |
| B端食堂 | 食堂管理者/厨师 | 了解菜品口碑、优化菜单      |

### 1.3 当前版本范围（MVP）

**当前版本包含以下核心功能：**

1. ✅ 菜品浏览与搜索
2. ✅ 菜品点评与打分
3. ✅ 周榜、月榜（各 Top 10）
4. ✅ 登录时偏好标签设置（仅保存到用户资料）
5. ✅ 转盘随机、卡片滑动两种选餐方式
6. ✅ AI 营养分析助手（RAG + 单轮对话）

**功能边界：** 推荐页及底部导航不设置独立的个性化推荐列表。登录时选择的偏好标签仅用于个人资料展示，不参与转盘和卡片候选池的过滤、排序或抽取。

### 1.4 平台形态

**Web 网站**，采用竖版优先布局，适配手机屏幕和移动端浏览器。

### 2.4 排行模块（FR-RANK）

#### FR-RANK-01：周榜/月榜

| 榜单类型 | 说明               | 更新频率           | 计算逻辑                        |
| ---- | ---------------- | -------------- | --------------------------- |
| 周榜   | 本周综合表现最高的 Top 10 | 每周一 03:00 定时任务 | 统计本周（周一~周日）点评的综合评分，结合评分人数计算 |
| 月榜   | 本月综合表现最高的 Top 10 | 每月1号 03:00     | 统计本月点评的综合评分，结合评分人数计算        |

**评分人数系数（防刷榜）：**

- 评分人数 ≥ 50：系数 = 1.0（完全可信）
- 评分人数 < 50：系数 = 评分人数 / 50（样本越少，加权越低）

**示例**：某菜综合评分 4.8，但只有 10 人评分 → 加权分 = 4.8 × (10/50) = 0.96

#### FR-RANK-02：排行榜页面交互

- 顶部 Tab 仅切换「周榜」「月榜」
- 每条记录展示：排名、菜品名、评分、评分人数、所属窗口
- Top 3 高亮展示（金/银/铜标识）

### 2.5 选餐决策模块（FR-DECIDE）

第一层只保留三个并列入口：「转盘」「卡片」「榜单」。本次会话进入某个入口后不切换模式，避免丢失当前选择状态。直接搜索不作为选餐入口，放在所有菜品页面。

| 模式   | 适用人群       | 核心交互                        | 输出                 |
| ---- | ---------- | --------------------------- | ------------------ |
| 转盘   | 完全没有想法的用户  | 先选择食堂，再从该食堂所有窗口中随机抽取一个窗口    | 1 个窗口，可重新抽取或查看窗口菜品 |
| 卡片滑动 | 想比较多个选项的用户 | 菜品卡片逐张出现：喜欢右滑，不喜欢左滑，也支持按钮操作 | 喜欢清单，必要时进入第二轮筛选    |
| 榜单   | 想参考热门菜品的用户 | 查看周榜或月榜 Top 10              | 榜单列表、菜品详情和评价入口     |

**三层页面结构：**

1. 第一层：选择转盘、卡片或榜单。
2. 第二层：转盘选择食堂后进入抽取；卡片选择食堂后进入卡片浏览；榜单选择周榜或月榜。
3. 第三层：展示转盘抽取的窗口及其菜品、卡片喜欢清单或榜单菜品；具体菜品均可进入菜品详情。

**偏好标签规则：**

- 登录时选择的口味、忌口和过敏标签仅保存到 `user_preferences`，用于个人中心展示和后续资料维护。
- 转盘和卡片候选池不读取这些标签，候选处理仅依据所选食堂的营业窗口及营业菜品数据。

**卡片滑动规则：**

- 右滑/点击喜欢：加入本次喜欢清单；左滑/点击跳过：本次会话不再展示。
- 喜欢清单超过 6 道时展示「再筛一轮」；第二轮只从喜欢清单中继续滑动。
- 支持撤销上一张操作；没有剩余卡片时展示喜欢清单和重新开始入口。

**MVP 验收条件：**

- 推荐页展示广告栏、待点评入口及「排行榜」「转盘」「卡片」三个入口。
- 转盘选择食堂后，可从该食堂所有窗口中随机抽取一个窗口，并支持重新抽取、查看该窗口菜品和进入菜品详情。
- 卡片可完成喜欢、跳过、撤销和二次筛选。
- 所有菜品页支持搜索框、食堂标签、楼层窗口浏览，并能进入菜品详情和评价页面。
- 榜单页仅有周榜、月榜两个 Tab，每个榜单最多展示 Top 10。

### 2.6 AI助手模块（FR-AI）

#### FR-AI-01：今日饮食营养分析

| 项目   | 说明                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------------------- |
| 触发方式 | 用户输入"我今天吃了 XX、XX、XX"，由系统解析菜品和数量后进行分析                                                                        |
| 处理流程 | ① 解析用户输入，匹配菜品库中的菜品<br>② 检索每道菜的预设营养数据（热量、蛋白质、脂肪、碳水、膳食纤维等）<br>③ 汇总计算一日摄入<br>④ 调用大模型，结合用户饮食目标（增肌/减脂/维持），生成分析报告 |
| 输出内容 | ① 总热量 + 三大营养素占比饼图<br>② 与每日推荐摄入量的对比<br>③ 营养均衡性评价（文字）<br>④ 改进建议（如"蛋白质摄入不足，建议晚餐加一份鸡胸肉"）                        |

**RAG 架构说明：**

```
用户输入
  ↓
[意图识别] → 提取菜品名 + 数量
  ↓
[向量检索] → 从菜品知识库中检索匹配菜品的营养数据
  ↓
[Prompt 组装] → 营养数据 + 用户画像 + 分析模板
  ↓
[大模型生成] → 结构化分析报告
  ↓
前端渲染（图表 + 文字）
```

#### FR-AI-02：健康问答

| 项目   | 说明                                   |
| ---- | ------------------------------------ |
| 功能描述 | 通用饮食健康问答，如"减肥期间食堂怎么选？"、"吃太油了怎么办？"    |
| 实现方式 | RAG 增强：将权威营养学知识（膳食指南等）存入向量库，检索后喂给大模型 |
| 兜底策略 | 如果检索不到相关内容，直接走大模型通用回答，并标注"仅供参考"      |

### 5.2 核心接口详细定义

#### 5.2.1 提交点评 `POST /api/v1/ratings`

**请求体：**

```json
{
  "dish_id": 123,
  "overall_score": 5,
  "taste_score": 5,
  "value_score": 4,
  "comment": "味道很棒，就是有点小贵",
  "quick_tags": ["推荐！", "分量足"]
}
```

**响应：**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "rating_id": 456,
    "dish_new_avg": 4.6,
    "dish_rating_count": 87
  }
}
```

**业务逻辑：**

1. 校验用户是否已点评过该菜品（查 ratings 表唯一约束）
2. 如有，更新记录；如无，插入新记录
3. 异步更新 dishes 表的 avg_rating 和 rating_count
4. 更新菜品评分和排行榜数据

#### 5.2.2 获取选餐候选 `GET /api/v1/decision/candidates`

**请求参数：** `mode`（roulette/swipe）、`cafeteria_id`；不接收用户偏好标签或窗口参数。`roulette` 返回窗口候选，`swipe` 返回菜品候选。

**业务逻辑：**

1. 根据 `cafeteria_id` 查询该食堂所有营业窗口；`swipe` 模式进一步查询这些窗口的营业菜品
2. 不读取用户偏好、忌口或过敏标签，不做过滤、排序或加权
3. `roulette` 返回窗口基础信息及菜品数量；`swipe` 返回菜品基础信息、评分、价格、所属窗口和标签

#### 5.2.3 转盘抽取 `POST /api/v1/decision/roulette/draw`

根据 `cafeteria_id` 从该食堂全部营业窗口中随机抽取一个窗口；重新抽取时排除本次已抽到的窗口，候选耗尽时提示重新开始。抽中窗口后，用户可进入窗口菜品页选择具体菜品。

#### 5.2.4 记录卡片行为 `POST /api/v1/decision/events`

记录本次会话中的喜欢、跳过、撤销和最终确认，用于恢复会话状态和统计功能使用情况。

#### 5.2.5 营养分析 `POST /api/v1/ai/nutrition-analysis`

**请求体：**

```json
{
  "food_description": "我今天吃了辣子鸡一份、番茄炒蛋半份"
}
```

**响应：**

```json
{
  "code": 200,
  "data": {
    "total_calories": 680,
    "nutrition_breakdown": {
      "protein": 35.2,
      "fat": 22.5,
      "carbs": 78.0,
      "fiber": 8.5
    },
    "daily_target": {
      "calories": 2000,
      "protein": 60,
      "fat": 65,
      "carbs": 260
    },
    "completion_rate": {
      "calories": 0.34,
      "protein": 0.59,
      "fat": 0.35,
      "carbs": 0.30
    },
    "ai_analysis": "今日午餐蛋白质摄入充足（59%目标量），但蔬菜纤维偏少，建议晚餐增加绿叶蔬菜。总热量控制良好，适合减脂期。",
    "suggestions": [
      "晚餐建议增加一份清炒时蔬",
      "可增加一份粗粮主食补充膳食纤维"
    ]
  }
}
```

**业务逻辑：**

1. 解析 food_description，提取菜品名称和数量
2. 根据菜品名称匹配菜品库并查询营养数据
3. 按数量比例计算实际摄入，汇总得出总摄入量和三大营养素
4. 根据用户 goal（减脂/增肌/维持）获取每日推荐摄入量
5. 组装 Prompt，调用大模型生成分析报告
6. 前端根据返回数据渲染图表

## 六、选餐决策详细设计

### 6.1 候选池规则

转盘和卡片均以用户选定食堂为范围，但候选粒度不同，规则如下：

1. 转盘查询该食堂全部营业窗口，窗口作为随机抽取的候选集。
2. 卡片查询该食堂所有窗口的营业菜品，菜品作为逐张展示的候选集。
3. 不读取用户偏好、忌口或过敏标签，不做过滤、排序、加权或匹配计算。
4. 直接搜索仅位于所有菜品页面，按关键词和页面筛选条件返回结果，不改变转盘和卡片候选池。

### 6.2 转盘流程

```
选择食堂
      ↓
查询该食堂全部营业窗口
      ↓
随机抽取一个窗口
      ↓
查看窗口菜品 / 再抽一次
      ↓
选择菜品并查看详情
```

重新抽取时排除本次已抽取的窗口；候选池耗尽后提示重新开始。

### 6.3 卡片流程

```
选择食堂
      ↓
加载该食堂所有窗口的菜品
      ↓
按菜品列表逐张展示卡片
      ↓
左滑跳过 / 右滑喜欢 / 撤销
      ↓
喜欢清单超过 6 道 → 二次滑动筛选
      ↓
确认最终菜品
```

卡片行为只用于当前会话的喜欢清单和二次筛选，不修改用户资料中的偏好标签；用户可在会话结束后重新开始。

### 6.4 状态提示

| 场景     | 展示文案                   |
| ------ | ---------------------- |
| 转盘候选范围 | "当前食堂全部窗口"             |
| 卡片候选范围 | "当前食堂全部窗口菜品"           |
| 转盘候选耗尽 | "本轮窗口已抽取完，重新开始"        |
| 卡片候选耗尽 | "本轮菜品已浏览完，查看喜欢清单或重新开始" |

### 8.2 关键页面交互说明

#### 推荐页

- 页面采用竖版手机布局。

- 广告栏下方展示上一餐待点评快捷入口，点击进入对应菜品点评页。
- 下方固定展示「排行榜」「转盘」「卡片」三个快捷入口。

#### 转盘页

- 先选择食堂（荟贤或聚雅），不选择窗口。
- 转盘候选池包含所选食堂的全部窗口，随机抽取一个窗口。
- 转盘停止后展示窗口名称、所在楼层及窗口菜品入口；点击具体菜品后进入详情页，详情页提供点评入口。

#### 卡片页

- 先选择食堂，卡片候选为该食堂所有窗口的菜品；不读取用户偏好标签。
- 顶部显示「已选 X 道 / 剩余 Y 道」和当前食堂，卡片区域保持固定尺寸，避免滑动时页面跳动。
- 支持触控左右滑、键盘左右键和「喜欢」「跳过」「撤销」按钮三种操作。
- 用户点击「查看喜欢」后进入清单；清单超过 6 道时优先展示二次筛选，不直接强制用户继续浏览。
- 二次筛选结束后，用户可确认一道菜、返回清单或重新开始；结束后回到菜品详情页。

#### 所有菜品页

- 页面顶部为搜索框，支持按菜品名称搜索，也可匹配食堂或窗口名称。

- 点击窗口进入该窗口菜品页，点击具体菜品进入菜品详情页；详情页提供点评入口。
- 无结果时提示更换关键词或查看当前食堂全部窗口。

## 十、数据初始化方案

### 10.1 菜品数据采集

| 方式     | 优先级 | 说明                                |
| ------ | --- | --------------------------------- |
| 手动录入   | P0  | 团队实地调研，先录入 1 个食堂的所有菜品（预计 50~80 道） |
| 拍照 OCR | P2  | 拍摄菜单自动提取菜品名（暂不纳入当前版本）             |
| 用户共创   | P1  | 允许用户"新增菜品"（审核后入库），快速扩充数据          |

### 10.2 营养数据来源

| 数据项          | 来源                | 精度     |
| ------------ | ----------------- | ------ |
| 热量/蛋白质/脂肪/碳水 | 《中国食物成分表》标准版      | 每 100g |
| 食堂具体菜品       | 根据食材配比估算          | 估算值    |
| 精确数据         | 后期接入专业营养数据库或实验室检测 | 精确     |

> **说明**：营养数据采用估算值（基于食材配比），在前端标注"参考值"。

### 11.2 安全要求

| 项目     | 措施                                                    |
| ------ | ----------------------------------------------------- |
| 鉴权     | JWT Token（Access Token 2h + Refresh Token 7d）         |
| 密码/验证码 | 手机号 + 验证码，验证码 5 分钟过期，每日限发 5 次                         |

## 十二、风险与应对

| 风险                      | 影响         | 概率  | 应对策略                                                                   |
| ----------------------- | ---------- | --- | ---------------------------------------------------------------------- |
| **候选数据不足**：食堂或窗口菜品录入不完整 | 转盘和卡片可选范围小 | 高   | ① 先完善荟贤、聚雅食堂窗口数据<br>② 候选耗尽时提示重新开始<br>③ 提示用户补充菜品信息                      |
| **菜品数据不全**：手动录入工作量大     | 用户搜不到想找的菜  | 中   | ① 先做荟贤、聚雅食堂基础数据<br>② 开放"新增菜品"功能（用户提交，审核入库）<br>③ 持续补充窗口和菜品数据            |
| **AI 幻觉**：大模型给出不准确的营养建议 | 用户信任度下降    | 中   | ① RAG 基于真实数据生成<br>② 所有 AI 建议标注"仅供参考"<br>③ 关键数据（热量/营养素）从数据库取，不让模型自由发挥   |
| **数据准确性**：营养数据为估算值      | 健康建议不够精准   | 中   | ① 前端明确标注"参考值"<br>② 定期校验营养数据<br>③ 提供"反馈纠错"入口                            |
| **评分刷榜**：恶意刷高分/低分       | 排行榜失真      | 低   | ① 每人每菜限评一次<br>② 评分人数加权（样本少权重低）<br>③ 异常检测（同一 IP 短时间大量评分自动拦截）            |
| **大模型 API 成本**：调用费用超预算  | 运营成本上升     | 中   | ① 对话上下文限制长度<br>② 设置每日调用限额                                              |
| **团队技术栈不熟悉**            | 开发进度延迟     | 中   | ① 第一周做技术 Spike（FastAPI + 前端联调 Demo）<br>② 关键模块提前写 POC<br>③ 预留 Buffer 时间 |
